# Formalization strategy

Source data: The Scheduling Zoo as read by `parameterized-scheduling-zoo`
(`data/schedulingzoo.json`): 747 problems, 26 notation fields, 121 upstream
reduction rules plus 13 added ones, 614 Hasse edges.

## Design in one paragraph

A *kernel* fixes what a schedule is and exposes `start` and `completion`. A
*field* over a kernel is a restriction (predicate on kernel instances), a
constraint module (extra data plus a condition on schedules) or an objective
(extra data plus a cost). A *specification* picks one value per field and
determines a `Problem`. Relations are proved once per field (`Sound`), and
`Assembly.lift_sound` turns any field-wise comparison of specifications into a
sound embedding. Real encodings that change the instance are separate, hand
proved embeddings.

## What exists

See `notes/CHECKLIST.md` for the current status, the open items and the
readings that still need confirmation. In short: 41 concepts, 98 statements
(all proved), all 747 problems of the zoo as specifications, 604 of its
edges checked by evaluation and 8 stated one by one (all proved).

Tools: `tools/coverage.py <schedulingzoo.json> -v` compares the formal
relations with the data; `tools/generate.py <schedulingzoo.json>` (run from
`tools/`) rewrites the catalogue concepts `Zoo*` and their proofs.

## Decisions

Settled in this draft:

- Restrictions are modules without data (`Module.ofRestriction`); a module
  has an admissibility condition on its data, which is how precedence classes
  are expressed.
- Field orders are `Bool`-valued, so `Spec.le` is decided by `decide`.
- Embeddings are data plus a separate `Sound` proposition. `lift` takes the
  family's soundness as an argument because the image instance must carry a
  proof of admissibility.

Open, to review before freezing the concepts:

00. **`R` is read with machine sets**, that is, a job may be forbidden on a
   machine, which stands for an infinite processing time. Then `P|M_j` and
   `Q|M_j` are field-wise special cases of `R`.

0. **`P2` is read as at most two machines**, and `n = 2` as at most two
   jobs. Under this reading the zoo's chain 1 ⊂ P2 ⊂ P3 ⊂ P is field-wise
   and sound. Under the reading "exactly two" it is not a special case for
   identical or uniform machines.

1. **Time and cost types.** Start and completion times are nonnegative
   rationals and costs are rationals, so that preemptive schedules and
   `L_max` fit. Instance data (processing times, release dates, due dates,
   weights) stay natural numbers.
2. **Uniform machines are missing** from the environment chain: `p_ij = p_j /
   s_i` needs rational processing times or a divisibility convention.
3. **Single machine is identical machines with exactly one machine**, as in
   the zoo's data, not a separate kernel. Preemptive and non-preemptive
   scheduling are two machine models over the same instances; the restriction
   fields are written once for every model.
4. **Deadlines may be `∞`**, so that "no deadlines" embeds field-wise.
5. **Precedence relations are arcs**, not required to be transitive or
   acyclic; a cyclic relation simply has no feasible schedule.
6. **Field orders are not required to be reflexive and transitive.** The
   present ones are; composition of embeddings does not need it.

## Phases

1. **Harden the core.** Done.
2. **Fill the parallel kernel.** Started. Remaining: the other precedence
   classes (tree, opposing forest, sp-graph, interval orders, bounded height,
   level order, dimension); `p_j ∈ {1,2}`; common deadline and common due
   date; machine sets (needs a `machine` accessor, so a kernel extension);
   job sizes; number of jobs; a fixed number of machines; time lags and
   communication delays; objectives `Z_j`, `L_max`, flow time; the parameters
   `p_max`, `#p`, `#d`, `#w`. Each upstream rule becomes one case of a
   field's `Sound`.
3. **Further kernels.** Preemptive parallel machines; shops (job shop, with
   flow shop as a restriction and open shop separately); batching; server and
   robot. Each new kernel reuses the generic modules. Relations between
   kernels are embeddings proved by hand.
4. **Encodings that are not field-wise.** The 19 multi-field upstream rules
   and the added eligibility rule (`M_j` into `R`), uniform into unrelated,
   machine count in shops via zero-length operations, threshold objectives
   (`C_max` inside `ΣU_j`). Each states its parameter bound explicitly; these
   are the arrows the converter refuses to carry parameters across.
5. **Generate the zoo.** A script emits one `spec …` line per problem from
   `schedulingzoo.json` and one `Spec.le` fact per Hasse edge, checked by
   `decide`. A comparison report lists edges of the data that the formal order
   does not derive, and conversely.
6. **Complexity layer.** Decision versions, `PolyReduction` / `FptReduction`
   and the transport of hardness up and algorithms down along sound
   embeddings, reusing the vocabulary of `TheoreticalInfra`.

## Risks

- Modules that are generic in the kernel only see `start` and `completion`.
  Fields that need more (machine sets, no-wait, transportation) require
  optional accessors; the kernel interface should grow by extension, not by
  editing `Kernel`.
- A sound embedding gives equal optima but says nothing about running time.
  Phase 6 needs size measures, and the high-multiplicity encoding changes
  exactly that.
- Soundness of a field quantifies over all kernels. A rule that holds only in
  some environments (the zoo's `fix_j` rules in shops) belongs to phase 4.
